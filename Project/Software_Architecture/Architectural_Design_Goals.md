# Exercise 1: Define Architectural Design Goals

| Goal ID | Design Goal | Description | Related Requirement | Priority | Justification |
|---|---|---|---|---|---|
| DG-01 | Maintainability | The system should separate the user interface, application logic, and data-access responsibilities so that changes to one part can be made with limited effects on the others. | NFR-06: Allow administrators to update platform room details and booking rules from the dashboard without editing the code. This applies to platform-managed information and does not give administrators control over external provider’s source listings or availability. | High | Separating responsibilities makes the system easier to update as features change. It also supports the project's distinction between platform-managed records and information supplied by DeskOS.Separating system responsibilities also helps developers update individual parts without unnecessarily affecting the entire platform. |
| DG-02 | Security | The system architecture shall protect user accounts, personal information, and booking operations through authentication, access restrictions, account protection, and verification of incoming external API callbacks. | NFR-02 – Security: The system shall require users to log in before making or cancelling a booking.<br>NFR-12 – Security: The system shall lock a user account for 5 minutes after 5 consecutive unsuccessful login attempts..<br>NFR-19 – Security: The system shall verify the signature of each incoming DeskOS callback before accepting and processing its booking-status update. | High | The system handles user accounts, personal information, and booking records. Security mechanisms are necessary to prevent unauthorized access and ensure that external booking-status updates are authentic.The platform should verify callbacks which helps in preventing unauthorized status changes. |
| DG-03 | Reliability | The system should continue operating when the DeskOS API is unavailable or unresponsive. It should handle failed or repeated API callbacks safely and avoid incorrect booking-status updates. | NFR-04 – Reliability: The system shall update space availability after a booking is made or cancelled, ensuring that the displayed availability reflects the latest booking status.<br>NFR-16: Handle unavailable or unresponsive DeskOS API responses without causing the platform to crash. NFR-20: Process duplicate DeskOS callbacks without updating a booking status more than once. | High | The platform depends on DeskOS for external space information and booking operations. Failures or duplicate callbacks must not crash the platform or create inconsistent booking records. |
| DG-04 | Performance | The system should process successful DeskOS responses and display the corresponding space information within the time specified by the project requirement under normal operating conditions. | NFR-01 – Performance: The system shall display space search results within 3 seconds under normal operating conditions.<br>NFR-18 – Performance: The system shall process a successful response from the DeskOS API and display the corresponding space information within 5 seconds under normal operating conditions, excluding delays outside the system's control | Medium | Users need search results without unnecessary delays. Meeting the specified response time makes the search process practical and improves the overall user experience. |
